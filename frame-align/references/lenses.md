# 软件框架的视角清单

做"补全"时用来检查框架上有没有被遗漏的面。它是提示，不是必填表。

挑与这个项目相关的用。一个命令行小工具不需要讨论部署拓扑，一个数据管道不需要讨论界面流程。不要把清单逐项变成问题抛给用户，那正是本 skill 要避免的机械做法。

这份清单与技术栈无关。技术栈本身只是其中一个节点，由你根据项目和用户的经历提议，不预设任何模板。

| 视角 | 要弄清的事 |
|---|---|
| 目标与用户 | 给谁用，解决他们的什么问题，做成了是什么样 |
| 范围 | 做什么，明确不做什么，第一版到哪里为止 |
| 关键流程 | 用户或数据从头到尾怎么走，最核心的一两条路径 |
| 数据与状态 | 有哪些数据，存在哪里，谁能改，丢了会怎样 |
| 技术形态 | 网页、命令行、服务、库、插件、移动端；用什么语言和框架；运行在哪里 |
| 外部依赖 | 要对接哪些已有系统、第三方服务、接口 |
| 约束 | 时间、成本、用户或团队已有的技能、必须遵守的规定、必须兼容的东西 |
| 质量要求 | 性能、安全、可靠性里，对这个项目真正要紧的是哪一样 |
| 验收 | 怎么知道它做对了，谁来判断 |

在已有代码上工作时，这些视角里的大部分可以从代码中读出来。读出来的内容作为陈述呈现给用户确认，不要再问一遍。
